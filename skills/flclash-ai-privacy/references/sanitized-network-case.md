# 脱敏案例：固定 AI 出口与网络稳定性排查

本案例记录一次 macOS 上 FlClash／Mihomo 的分流调整与短时观测。
它用于说明配置意图、验证方法和证据边界，不代表所有设备或时段的效果。
案例客户端为 macOS FlClash v0.8.98；应用前仍需核对本机实际客户端与运行内核版本。
离线使用 Mihomo v1.19.32 验证配置，不等于证明运行中的 FlClash 使用同一内核版本。
配套文件为 [分流增量参考片段](../templates/routing-policy.redacted.yaml)，不能单独导入。
住宅、节点、provider、端口、规则 URL、更新间隔和阈值均由使用者提供，片段只保留占位符。

## 当前策略

案例用户最终改回住宅直连，保留固定海外 AI 出口；香港链式连接只是可选比较路径。
此处“住宅直连”指客户端直接连接住宅代理服务，不代表 AI 请求绕过代理。
这里按 AI 供应商归属分类，不能按服务器 IP 地理位置替代业务分类。

| 流量类别 | 当前策略 | 需要保留的边界 |
| --- | --- | --- |
| 内网与私有地址 | 既有直连规则 | 保留原安全与拒绝规则 |
| 中国 AI 供应商 | DIRECT | 优先于既有 AI 住宅规则 |
| 海外 AI 供应商 | 固定住宅组，当前选择住宅直连 | 该组覆盖全部海外 AI，不只 Claude |
| 普通中国流量 | 既有中国直连策略 | 排在海外 AI 规则之后 |
| 其他普通流量 | 原规则与原 MATCH | 普通父组选既有 URLTest 组 |

中国 AI 供应商的国际站或海外 API 域名也可能按此策略 DIRECT。
这只是用户选择的供应商分类策略，不说明目标服务器位于中国或 DIRECT 必然最快。
规则集合可能遗漏新域名，真实连接的匹配结果仍需核对。

## 规则顺序与合并方式

保留既有安全／拒绝规则的优先级，再将业务规则按下列相对顺序合并：

1. 内网与私有地址的既有直连规则。
2. 中国 AI 供应商直连集合及已确认的补充域名。
3. 既有 AI 集合与海外 AI 集合，目标均为原固定住宅组。
4. 普通中国域名与 IP 直连规则。
5. 其余原规则，以及仍在末尾的原 MATCH。

中国 AI 必须先于可能同时包含这些域名的旧 AI 规则。
海外 AI 必须先于普通中国规则，避免较宽的直连集合抢先匹配。
中国直连集合是策略集合，不能视为每个域名服务器位置的证明。
原 AI provider 必须继续存在；示例里的 provider 与组名需要映射到本机实际名称。
不得用片段中的 rules 整体覆盖原列表，或删除原订阅、节点和自定义例外。

## 普通 URLTest 组的真实范围

本次仅让普通父组选中已存在的 URLTest 组，没有修改该组候选成员。
该既有组同时包含机场候选与自定义住宅候选，并不是机场专属组。
因此普通请求可能选中住宅候选，不能把“选择 URLTest”写成“普通流量全部走机场”。
若要排除住宅候选，必须另立明确变更，审查成员来源、过滤规则与回退路径。
不能在更新案例或运行排障 Skill 时顺手改组成员。
URLTest 比较的是其测试目标的探测结果，不是所有业务目标的速度与稳定性排名。
Fallback 则按候选顺序选可用节点，不能与 URLTest 混为一谈。
参考 [URLTest](https://wiki.metacubex.one/en/config/proxy-groups/url-test/) 与 [Fallback](https://wiki.metacubex.one/en/config/proxy-groups/fallback/)。

## 香港链式路径的定位

可选路径是“香港前置代理 → 同一住宅代理 → 业务目标”，最终出口应仍是该住宅。
前置是否更好必须按同目标、同请求类型和相近时段比较，不能由地域或节点名称决定。
本案例曾出现链式卡片 Timeout，而当时住宅直连请求仍可达。
这个结果不足以定位是前置、住宅路径、共同测速目标还是其他共享环节失效。
不能据此宣布链式永远不可靠，也不能宣布链式必然消除抖动。
Mihomo 已弃用 relay 分组；可选链式方案应检查实际版本并使用兼容的 dialer-proxy。
参考 [dialer-proxy 与 relay 迁移](https://wiki.metacubex.one/en/config/proxies/dialer-proxy/)。
本案例当前策略没有要求启用链式，也没有将它当成稳定性的默认前提。

## 短时观测与能证明的范围

下列观测来自不同阶段，并非严格同步的对照实验，不能直接推导长期优劣。

| 观测 | 支持的结论 | 不支持的结论 |
| --- | --- | --- |
| 网关短测 90 包，0 丢包 | 该采样窗口内网关探测正常 | 全天无丢包、满载时无排队或 Wi-Fi 永不抖动 |
| 某机场候选 3 次早期 TLS 错误 | 该候选到该目标的请求在当时失败 | 所有机场同时故障，或已定位故障责任方 |
| 普通新路径出现约 5–6 秒慢请求 | 新选择仍存在明显业务等待 | 已消灭抖动、普通路径始终最快 |
| 海外 AI 匿名 HEAD 返回 404，中国 AI 接口返回 401 | 请求到达目标的 HTTP 响应层 | 账号正常、认证成功、API 推理或流式响应成功 |
| 一个批次 30 次新连接成功 | 该批次请求成功 | 全天稳定、其他目标成功或以后不再 Timeout |

首次连接耗时包含连接建立、TLS 以及服务响应，不能直接称作网络 RTT 或抖动。
复用连接的后续请求通常省去部分建连成本；必须与首次请求分开记录。
应保留目标类别、请求方法、是否新建连接、失败阶段和样本量，公开时去掉关联标识。
匿名连通性探针无需使用真实 API Key，也不能替代获授权的实际业务验收。
TLS 或 HTTP 成功不代表 SSE、WebSocket、长时间推理与断线重连已经验证。

## 所有卡片 Timeout 时如何取证

诊断阶段保持当前住宅选择，不切组、不停核、不重载、不刷新订阅或主动全节点测速。
先只读确认物理接口、网关、核心进程、本地监听和已有连接匹配到的规则与代理链。
再沿当前路径，以少量请求比较实际测速目标和不同业务服务，分开记录 TLS 与 HTTP 结果。
若测速目标失败而业务目标成功，可考虑共同探测目标问题，不能直接说全部节点失效。
若多个业务目标均失败，也只能先定位当前共享路径，不能把未独立验证的节点判死。
TUN 开启时，不使用系统代理不等于绕过 TUN；不能把这种请求当作物理直连对照。
普通 IP 查询网站可能走普通 URLTest，返回值不能直接当作海外 AI 的实际出口。
确认 AI 出口时应核对该业务连接的规则与代理链；出口查询需要明确对应同一路径。
回环合成测试只验证分流行为，不能替代真实网关、DNS、机场或住宅路径测量。

## 隐私、账号与未完成验证

固定出口、DNS 隐私、住宅分类、地域资格与账号状态是不同问题，需分别验证。
供应商标注“住宅”不构成住宅身份、独占程度或长期 IP 分类的独立证明。
本轮最新测试没有确认 DNS、WebRTC 或 IPv6 的隐私效果；保留既有设置，另行验证。
TUN 接管流量不等于修复公网拥堵，udp 开关也不能保证 TCP 或 AI 请求稳定。
不要为本案例自动加入 BBR／eBPF 等平台不匹配的“抗抖参数”。
本参考不保证匿名、不保证不封号，也不将代理出口位置视为服务地域资格证明。
服务可用地区以 [Anthropic Supported Regions Policy](https://www.anthropic.com/supported-countries) 为准，不维护易过期的地区长名单。
账号限制应按 [官方警告与申诉流程](https://support.claude.com/en/articles/8241253-safeguards-warnings-and-appeals) 处理，不把反复换 IP 当作恢复账号的方法。
API 响应需区分认证、权限、限流与服务端错误，参照 [Claude API errors](https://platform.claude.com/docs/en/api/errors)。
公开案例不包含真实请求 ID；向官方支持提供所需标识时，应通过用户授权的私密渠道。

- 片段只作为增量参考；占位符未替换、依赖缺失或版本不兼容时停止导入。
- 核对原订阅、节点成员、DNS、TUN、监听端口和活动连接不会被无意更改。
- 用本机实际内核在受控环境检查合并后的配置；不要拿占位符片段宣称可直接运行。
- 公开文件排除住宅地址／端口、个人 IP、账号、节点名、profile ID、私有路径和订阅 URL。
- 不公开凭据、认证头、Cookie、原始日志、trace／请求标识、运行时备份或截图。
- CI AI 专用分流仅有离线代码与合成验证，本案例不声称服务器已部署。
- 报告应保留失败和慢请求，只描述已确认的行为，不承诺长期稳定或抖动清零。

把本案例复用于其他设备时，重新确认策略与证据；不要把这里的短测结果当作新环境的验收。
